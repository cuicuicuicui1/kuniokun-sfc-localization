## 原事件定位

| 对象 | 本游戏CPU地址 / WRAM | 本次意义 |
| --- | --- | --- |
| 事件安装 | `$07:8760` → `$07:8AE3` | `$1D22=88` 经原指针表安装事件08；不写脚本PC |
| 事件表/起点 | `$04:8000` / 事件08 `$04:9E68` | `$1BE4=1` 选择已结束入口战斗的站台分支 `$04:A04B` |
| VM状态 | `$1D23`，`$1D20/$1D21` | 当前事件与bank04脚本PC；不能用PRNG `$0348/$0349` 代替 |
| 战后对白 | `$04:A250..A3B4` | 原消息BF/C0/C1/C2/C3/C4；包含“安静下来了”“二十个人”“联合里还有更强的人” |
| 最终奖励消息 | `$04:A3BA`：`30 05 00` | 原消息0005由游戏生成，首段动态参数为 `DE B8 DE B9 DE 0D` |
| 原消息等待 | `$04:A3BD`：`31`，等待PC `$A3BE` | `$1D25 bit40` 由原 VM 检查 `$0373` 是否清零 |
| 后续事件 | `$04:A3EA`：`BF 09` | 奖励消息完成后，经原脚本转到事件09 |

**不把文本JSON的index直接当VM message参数**：主文本记录N对应原VM参数N+1。`$122B/$122D` 是战斗状态，不是全局剧情阶段。

## 死锁机制

`$09DD` 与 `$09DF` 是字节读/写游标；`$09DE` 是另一图形队列状态；`$09E0/$09E1` 是原 `$00:FC75` 写入的16位列车位移。rc4的 `$DE` 消费者把 `$09E0` 非零误认为队列繁忙，反复退回。

列车控制暂停期间，位移可以保留非零旧值，并不等于文字队列忙。本次旧版原事件奖励开始时 `$09E0/$09E1=0001`，即使DD/DF为0也不断重试；候选开始时位移为0006，却正常完成名称和消息。随后才执行原事件的后续控制，列车能够再次更新。

修复仍是 `Asm.queue_load_x()/queue_store_x()` 的字节协议及容量延期，不清零/占用相邻列车位移。候选新增的模型回归覆盖这个真实提示中的B8/B9/0D及位移1/6。
