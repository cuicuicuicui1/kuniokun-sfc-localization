## 1. 已修复：战斗名字牌真实缺陷

### 1.1 JML / RTL 调用约定不匹配

v38 在 `$00:8C91` 用 `JML $3E:D000` 跳入汉化钩子，但钩子的出口是 `RTL`。
JML 不压返回地址，RTL 却从栈中取三个字节，因而把调用者保存的 X 和其他栈内容当成返回地址。
本轮改成 **JSL**，恢复正确的长调用/长返回配对；保留原调用者的 PLX、RTS 路径。

这不是仅靠反汇编的猜测：Mesen 真实 CPU 的完整 `$00:8C34` 名字牌调用测试中，
v38 六个场景全部无法返回到预定调用点；修复版全部正常返回。

### 1.2 第二个字读成第一个字、单字名字尾部错读

旧代码用 `$18 & $FC` 定位四字节名字的开头，导致第二个汉字仍读第一个字的页号和字型号。
本轮改为按当前双字节对对齐：`$18 & $FE`。两字名字分别取各自字形；单字名字后的空格继续走原 FA/FB 路径。
旧测试虽然计算了第二个字形，却拿第一个字形作两次期望值，本轮一并修正。

### 1.3 上传数据覆盖未完成的队列头，游标又被调用者回写

真实调用链先在 `$8C45` 写四字节队列头，再在 `$8C48` 调取字函数，直到 `$8C57` 才提交队列游标。
旧钩子直接从 `$09DF` 开始上传，覆盖这四字节；即便只增加游标，随后调用者仍会用保存的 X 写回旧位置。

本轮在插入 72 字节字形数据前：

1. 将尚未提交的四字节头后移 72 字节；
2. 调整调用者栈里保存的 X，使后续 PLX 和队列提交跟随新位置；
3. 用完整 16 位游标检查余量，并为调用者后续最多 48 字节留空间；
4. 不再要求“队列必须为空”，避免第一个汉字上传后第二个字永远被跳过。

Mesen 实测：两字名字得到 **192 字节完整队列 = 4 个字形上传条目 + 8 个 tilemap 单元条目**；
单字名字 120 字节；繁忙队列保留已有条目并安全跳过新增字形，不写越 `$0BFF`。

**相对 v38，ROM 仅 461 个字节变化，全部位于名字牌钩点、其例程区域及校验和字段。**
对白、术语、字形库、正文排版及打字节奏本轮没有改写，避免把核心修复与翻译润色混在一起。

## 2. 已修复：测试和构建流程的“假通过”

- `verify_all.py <ROM>` 以前只显示参数，子测试仍读固定 ROM；现在在隔离副本中验证指定 ROM、IPS 和同目录元数据。
- 必需测试缺失以前被跳过后仍可能“全部通过”；现在立即失败。
- HUD / 道具消息测试以前默认看环境变量 OFF 而跳过；现在依据构建元数据和真实钩点判定。
- 菜单上传测试默认读旧的 `exp_c2.smc`；改为当前构建。
- IPS 校验以前读取 F 盘旧发布物，并且不一致仍返回成功；现在默认检查当前工程，严格解析 EOF/记录边界，不匹配返回非零。
- `check16.py` 的部分错误只打印而不失败；`verify16.py` 后半段的失败未统一反映到退出码；本轮补齐。
- 槽位表检查的右半表偏移漏算标签/名字槽；本轮修正。
- 组合测试以前会覆盖当前 IPS 和元数据；现在每个组合在临时副本中构建。
- 去掉 `check16.py` 未使用的 `mos65xx` 导入，避免无关依赖阻断检查。
- 构建与相关检查按脚本目录定位输入，不再硬编码旧工作区路径；构建强制要求 `PYTHONHASHSEED=0`。
- 补记 HUDFIX/ITEMSG/PACE/标签槽配置到构建元数据。
- 模型的 `DEC dp` 漏更新 N 标志，且未正确支持 M 宽度；完整四格循环因此可能无法退出。本轮修正并加 8/16 位负例测试。
- 新 HUD 回归执行 **整个 `$00:8C34` 调用链**，不再吞掉未支持指令异常来伪装“成功返回”。

## 3. 实际完成的验证

| 验证 | 结果与边界 |
|---|---|
| 自动校验 | 16 项自动检查通过；另有 1 项占用信息报告，不把它称为自动安全性证明 |
| 名字牌模型 | 560 条真实名字记录，4 个角色槽轮换；队列边界；假名/空白/汉字混合 |
| Mesen 完整调用 A/B | 两字、单字、跨页、已有 32 字节队列、繁忙 200 字节队列、假名；旧版 6/6 失败，候选版 6/6 通过 |
| Mesen 输出检查 | 逐字节核对实际 WRAM 队列的地址、大小、字形数据及单元数据；检查借用 RAM 恢复与队列边界 |
| IPS 往返 | 从干净原版应用补丁，逐字节等于候选 ROM |
| 可复现性 | 连续两次构建的 ROM、IPS、三个元数据文件 SHA-256 全部相同 |
| 校验器负例 | 把选定 ROM 的 JSL 故意破坏为 JML，校验返回非零；损坏 IPS / 不同目标 ROM 也确实失败 |
| 校验无副作用 | 校验前后当前五个构建产物哈希不变 |
| 正常按键样本 | 候选版 6000 帧；旧版同输入对照 1800 帧。没有命中自然战斗或状态屏，不能算这两项验收 |

**Mesen 定向回归使用了临时 ROM 副本中的复位测试入口，执行真实游戏例程，但不是自然游玩通关。**
它关闭中断后测试 ABI/队列，不能替代自然战斗中的 NMI 并发、消息并存或长时间压力测试。

## 4. 仍存在的汉化缺口和下一轮优先级

1. **文件命名界面仍是日文。** 正常按键样本进入了这一界面；v38 与候选版第 1800 帧逐像素相同。
   提示“ファイルのなまえ いれてください”、结束项“おわり”等尚未汉化，旧交接的“全部完成”不成立。
   对应截图：`未汉化_文件命名界面.png`。
2. **自然战斗 → 装备消息 → 状态屏联测未完成。** 本轮正常样本没有覆盖这些场景，不把“进程跑完”当成通过。
3. HUD 和消息内名字/道具名仍使用部分共用专用瓦片，需动态同屏压力测试，不能排除相互覆盖。
4. 四角色/多人模式、繁忙队列下名字切换、NMI 插入点与长战斗尚需验证。
5. 道具 toast 停留时间、破折号场景、对白语义/术语/遗漏的系统复核仍待推进。
6. 最后再按原要求做两个不同核心的模拟器验收；**本轮没有宣称完成双模拟器或通关验收。**

## 5. 重建与回归

在工程根目录执行（`$py` 指向可用 Python，需 Pillow）：

```powershell
$env:PYTHONHASHSEED = '0'
$env:PYTHONUTF8 = '1'
& $py cnbuild5.py
& $py verify_all.py
& $py tools/run_mesen_hud.py kuniokun_cn.smc --mesen F:/emulators/mesen2/Mesen.exe --tag local-check
```

指定候选 ROM 时，将 `cn_build_params.json`、`cn_addr_map.json`、`cn_glyph_cell.json` 放在其同目录：

```powershell
& $py verify_all.py path/to/candidate.smc --ips path/to/candidate.ips
```

`--skip-layers` 仅用于诊断子集，不算完整检查。
`hw/mesen_playtest.lua` 是按键样本工具，日志中的 `hud_calls` / `status_calls` 为零时，不得宣称覆盖战斗/状态屏。
