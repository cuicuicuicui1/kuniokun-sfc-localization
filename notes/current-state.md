### ✅ v33：消息里的道具名 —— 已修（用户报的"道具名使用时乱码"）



**现象**：战斗消息 `[道具名]装备了！` 里，名字显示成 4 个乱码字形。

**根因**：v23 给道具名编了**自己的码** `[$DE][8×16 id]`（字形在 `$3F:8000`）——

因为状态屏三行装备值不能共用池子。而**消息抽屉只认中文页码**，于是

`$DE` 落到固定字形那条路，`$DE` 和 id 各画一个错字形 ⇒ 2 个汉字 = **4 个乱码**（数目吻合）。



**修法**：抽屉分派里 `$DE`（`FIXED0 = $DF`，所以 `$DC..$DE` 本来就是空的）插一条

`BEQ` 到新例程 `$3E:D400`（354 字节）：



- 取**紧跟 `$DE` 的那个字节**当字形 id，从 `$3F:8000 + id*32` 取 32 字节 8×16 字形；

- 上传进**名字槽 `SLOT0 + (列 & 3)`** —— 一个名字的几个字在连续四列，`& 3` 必然互不相同；

- 写这一列的上下两格（地址用引擎自己的行表 `$FA8E`/`$FA7E`）；

- `INC $03E9` 吃掉 id 字节，然后 `JML $03:FA7A`（那里 `INC $036F` 一次 = 8×16 占 1 列）。

- **不能直接 DMA** —— 消息框是活动画面期间画的，所以走 `$0B00` 队列（同 v32）；

  队列快满就走 `defer`：`DEC $03E9` 抵消消费端那次自增，这帧不发队列。



**槽位账**：道具名最长 4 个汉字、同屏要 4 格 ⇒ 名字槽从 2 个扩到 4 个。

`2×(36+6+4) = 92 > 89` 差 3 对，所以把 **`LABEL_SETS` 3→2**（`2×(36+4+4) = 88 ≤ 89` ✓）。

**实测 `list=9`、36 槽、89 对全不变。**

⚠️ 代价：对话盒的说话人标签组从 3 组降到 **2 组** —— `build_slotpairs()` 的注释说

"对话盒同时最多两个标签可见"，所以 2 组本该够（第 3 组是余量）。**这一条要在实机上确认**：

连续两句都带说话人、上一句的行还在屏上时，第二个标签会不会被覆盖。



**验证**：新增 `test_itemmsg.py`（已进 `verify_all.py`，**14 项全过**）——

在 65816 模型里跑真实例程，核对：取对了 id、32 字节点阵逐字节等于字形库、

槽位 `SLOT0+(列&3)`（四列四个不同槽）、两条格子的地址与内容、`$03E9` 吃掉 id、

列只推 1、队列快满时不发队列且索引抵消。**一次通过**（v32 那轮修了三个 bug，这次复用了它的模式）。

另有启动冒烟（2200 帧）正常。







### ✅ v32：战斗 HUD 名字牌的第二条坏法（双字节码）—— 已修



**现象**：翻译过的名字记录是 `[页][id]` 双字节码，而名字牌 `$00:8C83` **逐字节**查 FA/FB，

于是一个汉字被当成两个单字节 ⇒ 2 个汉字显示成 **4 个错字形**（用户截图里那个 `=○Θ`）。



**修法**：`$00:8C91`—`$00:8CA2`（18 字节，全 ROM 唯一调用者 `file 0x0C48`）改成

`JSL $3E:D000` + 14 个 `EA`，NOP 滑进原来的 `PLX`。新例程 584 字节：



- 判据用**记录的第一个字节**（`rec[$18 & $FC]`）：≥ `$C0` 走双字节路，否则原样走 FA/FB。

  ⚠️ 这里踩过坑：**不能看当前格那个字节** —— 奇格读到的是 id 字节（常常 < `$C0`），会走错路。

- 映射：格 k → 字形 `k>>1`，`k` 偶取左半、奇取右半（4 字节记录 = 2 个 16×16 字形 × 2 列）。

- 字形进**现成的 name pair 槽 42/43**（池永远不碰），所以**瓦片账一字未变**。

- **不能直接 DMA 到 VRAM** —— 名字牌是活动画面期间每帧画的，只有强制消隐期才能 DMA。

  改成走**引擎自己的 `$0B00` 上传队列**（`$00:8385` 在 VBlank 刷）：两条 36 字节 tile 条目，

  内联 32 字节点阵；游标快满就这帧跳过（字形上过一帧后一直有效）。

- 零页纪律：调用者占 `$17 $18 $20 $21 $22 $23`，临时值走**栈 + `$1E`（池偏移量）**。

  ⚠️ 两个坑都是模型测试抓出来的：**`TAY` 前 Y 必须是 16 位**（池偏移量最大 32704，8 位 Y 会丢高位）；

  **不能从栈上 `PLA` 取偏移量**（栈顶是 bank，会取到 `$21`）。



**验证**：新增 `test_hudname.py`（已进 `verify_all.py`，13 项全过）——

在 65816 模型里跑真实的 `$00:8C83`，逐格核对：4 格分别取 42/43 两个对的左右半、

两条队列条目的 VRAM 地址（`$6000+tile*8`）与**内联的 32 字节点阵逐字节等于字形库**、

奇格不上传、单字节码仍走 FA/FB 且零队列写入。

另外启动冒烟（Mesen2 无头跑到剧情对话 1800 帧）正常。







### ✅ v31：文字"还没读完就滚走了"—— 已修（一字节）



**根因（实测 + 反汇编）**：消息引擎每画一个字符走 `$03:EEE5`：

`LDA #$08 / JSL $009AB6`（等 A 帧）→ 也就是**每个字 8 帧**。

原版一行 26 个假名 ⇒ 一行停留 `26×8 = 208` 帧；

一个汉字占 **2 格**，我们一行只有 **12 个汉字** ⇒ 一行只停 `96` 帧。

**不到一半**，所以"还没读完就滚走了"。这也解释了为什么之前三轮换行节奏的测量都和原版一致

（换行机制没坏，坏的是**每行装的内容量**）。



**修法**：`rom[0x1EEE5+1] = 0x10`（8 → 16 帧）。一行停留 → `12×16 = 192` 帧，与原版 208 差 8%。

整条消息的总时长基本不变 —— 中文表达同样的意思用的字数约为假名的一半 ✓。

`$03:EE9D-EEAA` 那条"按住键 3 倍速"的快路径**没动**，所以按住键照样能快进。



**实测**："只开头按 A、之后零输入"跑 3000 帧，逐字间隔平均值：



```

原版 19.8 帧/字（一行 26 假名 → 约 515 帧/行）

v30  23.1 帧/字（一行 12 汉字 → 约 277 帧/行 = 原版的 54%）

v31  35.1 帧/字（一行 12 汉字 → 约 421 帧/行 = 原版的 82%）

```



**这个值是个一字节旋钮**：`rom[0x1EEE5+1]`。如果还嫌快，把它改成 `0x14`（20 帧，约等于原版的 102%）就行。

### 问题 A 的修法（强模型给的，**我已把细节补齐，但发现它也撞瓦片账**）



**调用链已逐字节解出**（原版 `file 0x0C34`—`0x0C82`）：



```

$8C34  LDA #$03 → $17          ; 循环 4 次（$17 = 3..0）

$8C38  LDY $10 / TYA / ASL ASL ; $18 = 角色槽 × 4  ← 名字记录里的字节下标

$8C3F  JSR $8BF7               ; 从 $00:8C2C 表取牌位（$7846/$7855/$7886/$7895）

$8C48  JSR $8C83               ; ★ 取这一格的字形 → $22(上) $23(下)

$8C4B  …写队列 2 个字：[$22,$24] 到上行

$8C5D  JSR $8C21               ; 队列指针跳到下一行

$8C60  …写 [$23,$24] 到下行

$8C6F  $20/$21 += 1            ; 列 +1

$8C7C  INC $18                 ; 下一个记录字节

$8C7E  DEC $17 / BPL $8C42     ; 4 次

$8C83  LDY $10 / LDA $1C03,Y / AND #$20 / BEQ ret

$8C91  LDY $18 / LDA $1B46,Y → TAX

$8C97  LDA $03FA9E,X → $22     ; ★ 钩点（4 字节，正好换 JSL）

$8C9D  LDA $03FB9E,X → $23

```



**⇒ 牌位 = 4 列 × (上行 1 格 + 下行 1 格)，每列 8 宽 × 16 高。**

**映射（这是关键，我之前推错过一次）**：一个 4 字节名字记录 = 2 个字形，

**每个字形占 2 列**（16×16），所以



```

格 k (0..3) → 字形 g = k>>1，列半边 half = k&1

记录里两个码的位置：g=0 → 字节 slot*4+0/+1，g=1 → 字节 slot*4+2/+3

   （入口 X = rec[$18]；页字节在 ($18 & ~1)，id 字节在 ($18 & ~1)+1）

left pair  = (UL, LL) = SLOTPAIR[sl], [+1]

right pair = (UR, LR) = 右半表[sl], [+1]

k=0/2（half=0）→ $22 = 左对基址，$23 = 左对基址+1

k=1/3（half=1）→ $22 = 右对基址，$23 = 右对基址+1

```

这正是 `build_slotpairs()` 里 **"a glyph gets two pairs: a left and a right"** 的用途

（`left = ... lab[0:need:2]`、`right = ... lab[1:need:2]`），

也解释了 `LABEL_GLYPHS = 2 # a four byte record holds two glyphs`。



名字字形存储（已确认）：**64 字节/字形**（4 瓦片 = 16×16），

`off = POOL_ROM + page*0x8000 + (LABEL_ID0 + idx)*POOL_STRIDE`（`POOL_STRIDE = 64`），

码 = `[PREFIX0 + page][LABEL_ID0 + idx]`。名字字形槽 = 槽位表里

`SLOTS + LABEL_GLYPHS*LABEL_SETS + g` = **42 / 43**（现在的 LNG=2 正好两个）。



**⚠️ 但它撞瓦片账，强模型没说**：

牌位是**每个角色一块**，而 `$00:8C2C` 有 **4 个角色槽**、`$1C03,Y` 的 bit5 逐槽控制画不画。

用户截图上是**同时两块**（两条旁各一块）⇒ 需要 **4 个名字字形**（2 块 × 2 字形）⇒ `LNG` 要 4

⇒ 就是上面那段实测的 **SLOTS 36→34、`list=9`→`list=4`**。✗ 不可接受。



**⇒ 所以 A 和 B 是同一个矛盾：都要"池子以外的 2~4 对瓦片"，而现在只剩 1 对。**

**真正的第一步应该是先解决"腾出 4~6 对自由瓦片"，A 和 B 才有得做。** 候选：



1. 逐瓦片核对 `protected_tiles()`（68 个）里有没有可以让的 —— 让掉的瓦片会被池覆盖，

   要让也得先确认没有别的码画它。

2. 主张"名字字形不进槽位表、直接占用**标签存储页之外的固定瓦片**" ——

   但那批瓦片同样要从 256 个里出。

3. 换个方向：**牌位只有 1~2 块常显**（只有玩家那个角色常画），

   如果实测只有 1 块，那 LNG=2 就够，一分钱不花。**这条要先实测**：

   在 Mesen2 对 `$00:8C89` 下断点，读 `$10`（角色槽）和 `$1C03,Y`，

   看一帧里有几个槽的 bit5 是 1。



**顺带**：强模型指出 HUD 的裸瓦片 `F2/64/EF/E7/F7/20` + 数字表 `$00:AFD4`（`10-19/21-26`）

有一部分在池的可达集里，应进保护集 —— 这同样会动瓦片账，一起算。

后者的具体嫌疑：DMA 通道 2 的 `$4320-$4326` 被我覆盖，游戏若也用这个通道，

它的下一次 DMA 就会拿我的参数跑（源地址 `$3F:8000+Y`、长度 32、目标 VMDATAL）。



**二分构建**：`bisect-items-only.smc`（CRC32 `CBF93010`）—— 只汉化道具名，

标签脚本保持原版（槽位表全 `$FF`，钩子恒走原 FA/FB 路径）。

用它定位是道具钩子还是标签钩子。



**其他可查方向**：`$1E`/`$1F` 作为暂存字节可能与 NMI 冲突；

标签钩子每次状态画面要跑 23 次 DMA，道具钩子约 10 次。



**如果都不行**，退路是：把 23 个标签字形烘焙进 `stat` 组腾出的 28 个瓦片

（那些假名码已不再被绘制，瓦片保护纯粹是为了撑 KEEP1），标签不再需要运行时上传；

代价是标签汉字要减到 14 个左右。



### 8×16 字形阈值（v25，重要）



`cnfont8.render8x16` 把 16px 字面用 LANCZOS 缩到 8 列再二值化，这个平均过程会把笔画灰度

压得很低。构建原来沿用 16×16 的 `GLYPH_THRESH=140`，结果 8×16 字形全是散落的横线——

连「力」都认不出。**v23 和 v24 的道具名/标签字形都受这个影响。**



实测（等验器鞋攻御运力最敏）：140 碎、**100 干净**、70 偏粗但仍可读、45 笔画粘连。

v25 起 8×16 走独立的 `GLYPH8_THRESH = 100`；16×16 是另一个函数（`cnglyph.render16x16`），

仍用 `GLYPH_THRESH`。



**仍未解决**：8 像素宽对复杂汉字本身就不够——最/器/鞋/敏/御 这些笔画多的字在 8×16 下仍然发糊。

标签列宽是够放 16×16 的（左列 16 格、右列 14 格，最长标签 4 个汉字 = 8 格），

所以下一步可以把标签改成 16×16：钩子照道具名那套写 4 格 2 列，字形表 stride 从 32 改 64。



### 状态画面标签（v24）



16 个标签块在脚本 ROM `0x00F9DB`，由解释器 `$01:F971` 逐格取 `FB[code]`（上半）与

`FA[code]`（下半）写 tilemap。和道具名同一个毛病：它不上传字形，而字形池会覆盖那些假名瓦片。



**试过但走不通的路**：把 23 个汉字烘焙进字体瓦片（`cmdwin_static` 那套）。代价 23 对瓦片，

空闲瓦片对从 89 掉到 66，`SLOTS` 从 36 掉到 34 —— **着色窗口直接从 `list=9` 崩到 `list=4`**。

游戏一屏能显示 9 条以上的列表，那是实打实的安全性回退，不能接受。



**最终做法**（与道具名同构，零瓦片成本）：



- 标签码的 `FA` 改成 8×16 字形号（`FB` 不用），解释器钩子挂在 `$01:F9BC`，代码在 `$3E:CC00`。

- 槽位由**码位**决定，不是光标：23 个标签同屏，只有码位能区分它们。

  一张 256 字节表 `$3E:CB00` 给出 code → slot（`$FF` = 不是标签码，走原路径）。

- 标签占槽位 **0..22**，道具值占 **24..35**（基址 24/28/32，每段 4 槽）。两者互不重叠。

- 状态画面上没有对话文字，所以这些槽位就是池子自己的槽位 —— 不必额外保护任何瓦片。



**代价**：正文的着色窗口保持 `list=9`、`SLOTS=36`、池子 923 个字形，与 v22 完全一致。



**顺带的两处取舍**（为了塞进 36 个槽位）：



- `stat` 保护组**保留**，但理由变了：脚本的假名码已不再被绘制，保护它们的瓦片纯粹是为了让

  `derive_keep1` 把那 58 个假名留在 KEEP1 里 —— KEEP1 一缩水，正文汉字变多、窗口变大，

  反而撑不住 `list=9`。这条理由写在 `PROTECT_GROUPS` 的注释里。

- 10 条道具名压到 4 个字符宽（摩托车钥匙→摩托钥匙、韦驮天衬里→韦驮天衬 等），

  让每段占 4 槽而不是 5。



**验证**：`test_labeldraw.py` 跑真实解释器，逐格核对 170 个 tilemap 字与 544 个上传字：

每个字形进自己的槽位、上传的就是该字形的点阵、名字栏与冒号仍走 FA/FB、标签槽位不越界。

`verify_all.py` 12 项全通过。



### 道具名：从"确诊"到"已修"（v23）



**问题**（v22 实测）：状态画面三个装备值由 `$01:FC75` 绘制，它只写 tilemap 编号、不写字形，

依赖字体块里的假名；而字形池会覆盖其中 45 个瓦片（`hw/clashwatch.lua` 实测：正常游玩中

18/45 被改写且永不恢复，因为字体块全 ROM 只有一处 DMA，在开机时装一次）。



**为什么不能走池子**：状态画面同时显示 3 个任意装备，任意两条道具名的汉字都可能同屏，

即全部道具名汉字必须两两不同槽（约 300 个），远超槽位上限。所以必须自己上传字形。



**解法**：给道具名一条**独立编码**，不占池子、不进着色、不保护瓦片。



- 码 = `[$DE][8×16 id]`。`$DB..$DE` 本来是空的：抽屉的中文范围到 `$DA`，单字节码从 `$DF` 起。

- 字形 = 独立的 8×16 表，`$3F:8000 + id*32`，201 个汉字。用 8×16 而不是对话的 16×16，

  因为一个值一列一个字符、旁边标签列只留 12 列，16×16 会把可用列数减半。

- 渲染器 = 挂在 `$01:FCA5`（原 `LDA $03FB9E,X` 那 4 字节），代码在 `$3E:C800`。

  遇到 `$DE` 就上传字形并自己写 tilemap；其它字节（数字、标点）原样走 FA/FB。

- **槽位来自 VRAM 光标，不是构建期着色**：三个值同屏，只有光标能区分它们。

  光标 `$79C6`/`$7A06`/`$7A46` → 槽位基址 0/12/24，值内每列进一个槽。

  这样三行的汉字永不撞槽，且所有槽位都 `< SLOTS`，不会碰到说话人名标签对。



**验证**：



- `test_itemdraw.py`：65816 模型逐条跑 110 条道具名，断言每个字形进自己的槽位、自己的

  瓦片对、上传的 32 字节就是该字形的点阵；数字仍走 FA/FB；三行分别用基址 0/12/24。PASS。

- `verify16.py` 的文本 round-trip 与绘制仿真已适配（道具名走独立编码，绘制仿真跳过该表）。

- `verify_all.py` 11 项全通过。

- 构建两次逐字节一致。

合计 1009 字节，装在 19931 字节的 bank $03 文本空间里，余 551 字节。`NO_TRANSLATE` 现已为空。



**仍未做**：状态画面的 16 个标签块（さいだいたいりょく 等）还是日文。它们可以照同一思路

处理——静态脚本文本，26 个汉字烘焙成 8×16 即可，列宽已验算够用。但那是下一步。

### 两个被证伪的旧补丁（已从构建移除）



1. **v31 打字机节拍（$03:EEE5 的 `LDA #$08`→`#$10`）= 空操作**。

   `$00:9AB6` 根本不是"等 N 帧"——它是 **$0B00 上传队列的空间分配器**：

   `LDA $09DD/CMP $09DF`，队列空则把两个游标清零，否则返回 `A+写游标`；

   恒 CLC 返回，且**返回值与参数在这条调用链上都被丢弃**。它后面的 `BCS`

   测的是**陈旧的进位标志**（RTL 不恢复 P）。实测：原版与 v36 的开场打字

   逐帧一致（37 个消息段全部吻合）。

2. **v36 系统消息计时器（$00:AEA5 的 40→100 帧）= 死代码**。

   bit5/bit6 永远为 0，整个 `$00:AE7B/$00:AE86/$00:AE95` 例程簇不会执行

## 场景驱动器状态机（重构①，2026-09-25 整理）



消息相关的完整控制流（全部实测/反汇编验证）：



```

主循环 $00:F2AA 每帧

  └─ JSL $00AE95        (死代码: $FFBE=ROM常量0, 见 v37 节)

  └─ ... $0322 在部分路径 INC

  └─ JSL $03:EB07       消息引擎 tick（47 个调用点之一）



$03:EB07 tick（每轮一次，逻辑 30Hz → 每 2 真帧）

  ├─ $0373 bit7? ─ 是 → 打字路径:

  │    ├─ $EF2D 行内节拍(E0 相: 打完一行的驻留, 计数 $0371/$03C1)

  │    ├─ $EF5E 滚动请求($0374 bit5: $F4 触发) → $EFB7 擦格动画(8帧/格×2)

  │    ├─ $F018 擦屏进行中($0374 bit7: $F0 触发, 4段×58轮) → 完成后复位指针

  │    ├─ $F0F1 停顿($0374 bit4: $F7 触发, 计时 $0392)

  │    ├─ $FA0B 擦 5 格($0374 bit3: $F6 触发, $038A 计数, 6轮/格)

  │    └─ $EEE5 每字绘制(至多 3 次/轮; bit7+按A → 3次/轮快进)

  │         └─ [v37 钩子: $3E:9800 节拍门, 每 PACE 次尝试放 1 字]

  │         └─ $FA30 画 1 格(8B 队列条目) / $FC9E 控制码($F0-F7)

  ├─ bit6(下一条已备) ─ 是 → $EB9E 装载下一条到 $03EA 缓冲(遇 $F3 停)

  │    └─ 装载完 → $EB5B 清框? / TSB bit7

  └─ 空闲(无 bit7/bit6):

       └─ $EEC7 闲置计数 $03A9++; ≥240轮($F0) → $FCC8 擦屏一次

          ($03A8 一次性锁存: 触发后除非 $0373 再变化, 不再自动触发)



说话人宏 $E2: 装载器在缓冲填充时展开(名字记录 4B 从 $034C 槽), 抽屉看不到 $E2。

词表(菜单 toast 如"道具没有带")走同一 $EB9E/$EB07 通道, 条目 = 消息脚本格式。



"过场停顿" Anatomy: 消息段间 570-720 真帧 = $F3 结束(闪光标等A) + 玩家未按 +

  240轮闲置擦屏 + 场景驱动器自己的节拍($1CA2, 03→88)。

  A 键在 bit6 装载检查里每轮都有效 → 按住 A 可跳过全部等待(实测 27000 帧零停顿)。



禁止改动清单:

  - $03:EED8 (闲置 240轮) — 砍半实测停顿反噬(900+帧, v38 实验)

  - $00:9AB6 参数 — 队列分配器, 非等待

  - $00:FFBE 相关 — 死代码

  - $0322 — 非帧计数器(仅部分路径递增)
