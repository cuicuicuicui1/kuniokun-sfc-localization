## 2. 快速开始

### 使用补丁

1. 自备上述 CRC32 / SHA-256 的合法原版 ROM。
2. 用支持 IPS 的补丁工具把 `kuniokun_cn.ips` 打到**原版副本**，保留原版。
3. 核对结果大小及 CRC32 **`AB1795B9`**，冷启动模拟器。
4. **不要加载旧汉化版的模拟器即时存档**：其内存可能保留错误滚动量。普通游戏内 SRAM 存档无需删除；请先备份。

此前在用户的 Snes9x 1.63 环境中，“声音同步 / Sound Sync”开启曾导致启动黑屏，同一 ROM 关闭该选项后可启动。
这只是该环境已复现的绕过方案，不是所有黑屏的通用结论；仓库脚本不修改玩家模拟器配置或存档。

### 本地重建（Windows / PowerShell）

要求 Python 3、Pillow；当前字体路径依赖 Windows 自带中文字体（如 `C:/Windows/Fonts/msyh.ttc`），16×16 字库输入为自备的 `fonts/unifont.hex.gz`。
字体文件、Python/Pillow 版本或构建环境变量不同可能改变输出；这些资源不随仓库分发。
请在仓库根目录、新的 PowerShell 会话执行，避免继承实验用 `PACE`、`STALEROW`、`BASE_ONLY` 等覆盖参数。

```powershell

# 自备 Unifont hex gzip 放到 fonts/unifont.hex.gz
```

构建写入当前目录的 `kuniokun_cn.smc`、`kuniokun_cn.ips` 与 `cn_*.json` 构建元数据；请在独立副本中重建，不覆盖需要保留的旧发布物。
`verify_all.py` 在临时副本中运行，不回写被测发布物；`--skip-layers` 只是诊断子集，不是发布验收。

## 5. 汉化方案（为什么是这样）

### 5.1 汉字占两个字符格，16×16 点阵

原版假名是 8×16（一格）。汉字如果也压进 8×16，笔画多的字（警/聯/襲）会糊成一团——实测过。
所以汉字用 **16×16，占两个字符格**，一行最多 13 个汉字（原版 26 个假名）。译文按这个宽度排版。

### 5.2 字形池 + 槽位表 + 上传队列

SFC 的 VRAM 只有 64KB，字体窗口只有 256 个瓦片，装不下 923 个不同汉字。做法：

* **字形池**：所有汉字点阵放在 ROM `0x108000` 起（bank $21），每个 16×16 字 = 64 字节 = 4 瓦片。
* **槽位表**：`$3E:8180` 每槽 2 字节 = 两个**独立**瓦片对（左半 t/t+1、右半 u/u+1）。
  一个汉字画之前，把它的 64 字节经上传队列送进这两对瓦片，再写 tilemap 条目。
* **上传队列**：WRAM `$0B00` 页，游标 `$09DD`（已刷）/`$09DF`（已追加，页号在 `$09E0`），
  条目格式 `[VRAM 字地址 2][$2115 1][字节数 1][数据…]`，由 VBlank 里的刷写器 `$008385` 搬进 VRAM。
  余量判据是 `$09DF < 0x101 - 本次字节数`（**不能**用 `$009AB6` 的 carry，它永远清）。

### 5.3 构建期图着色（这是安全性的全部来源）

两个不同汉字如果共用一对瓦片、又可能同屏出现，就会串字。构建期用图着色保证不会：
把"可能同屏出现的字形集合"建成窗口（主剧本按连续 1 条讯息、列表类按连续 9 条），
窗口内的字形两两相邻，用 DSATUR 分配 36 个槽位。

**窗口越大越安全**，而槽位数就是窗口的价钱。当前 `main=1 list=9`、923 字形、36 槽、89 对自由瓦片。

> ⚠️ 实测教训：**压缩译文不会腾出瓦片**。把最长的 8 条正文各压掉 2–4 字后构建确实通过了，
> 但着色窗口从 `list=9` 掉到 `list=3` —— 那是**降低安全性**。已撤销。

### 5.4 固定提示：选择框（はい／いいえ → 是／否）

选择框**不是**文字绘制的，是三段**绘制脚本**（`$03:F465` / `$F47B` / `$F491`），
每段格式 `[写进 $040A 的字节下标][字节数][(瓦片号, 属性)…]`，整块 64 字节上传到一行
（`$7BA0` / `$7BC0` / `$7BE0`，行地址表 `$03:F455`/`$F458` 按 `$0395` 索引）。
原版文字行只有 8 像素高（假名是单瓦片 `$44/$45/$46`），装不下汉字，所以**行数不变**、
两个选项改成 16×16：上行放 (TL,TR)、下行放 (BL,BR)。光标箭头瓦片 `$47` 必须一起保护，
否则会被字形池覆盖。

> 这段区域**曾被当成"文字"做过盲 kana 改写**，把角瓦片的翻转属性 `$A4` 改成 `$54`，
> 还把提示集 1 的块指针 `$F4AD/$F4C1/$F4D5` 改坏（真跑进去会写坏 `$040A`）。
> `checkchoice.py` 现在断言该区域的非瓦片字节与原版逐字节相同。

### 5.5 Start 菜单：从字形池里画（气力／道具／装备／状态／扔掉）

命令窗口的标签由引擎自己画（`$03:F992` 循环读 `$040A,Y` → `LDA $FB9E,Y` 取上半瓦片，
下半在 `$F9B5`），标签串由 `$03:F940` 从 ROM `0x01F743` 拷进 `$040A`。

* **单字版**（`CMDWIN=1`）：把 5 个汉字烘进字体块、给 5 个用不到的码重新指向它们，
  用"字形池永远用不到"的**单张空闲瓦片**（池子上传半边必须是连续两张）——不占预算。
* **两字版**（`CMDWIN=2`，默认）：标签改成**从字形池里画**。标签字形作为普通池字形参与着色
  （10 个字形同屏、互不同槽），每个字形用两个 1 字节码把槽位的 t/t+1 与 u/u+1 写进 FA/FB 和单元表；
  缺的瓦片数据由一个 **236 字节 stub**（`$3E:C600`）在菜单打开后的头几帧从池子搬进上传队列
  （每帧 3 个字形，4 帧搬完）。**槽位数与着色窗口与单字版完全相同**（36 槽、`list=9`）。

### 5.6 状态画面：标签与装备值

状态画面（`-- STATUS --` 那一屏）有三条独立的绘制路径，全部汉化：

- **16 个标签块**在脚本 ROM `0x00F9DB`，由解释器 `$01:F971` 逐格取 `FB[code]`（上半）
  与 `FA[code]`（下半）写 tilemap。钩子挂在 `$01:F9BC`：标签码的 `FA` 改成 8×16 字形号，
  槽位由**码位**决定（23 个标签同屏，只有码位能区分它们），占槽位 0–7、9–23。
- **三行装备值**（ぶき／うらじ／くつ）由 `$01:FC75` 绘制。它只写 tilemap 编号、不写字形，
  而字形池会覆盖它依赖的那些假名瓦片。改成独立编码 `[$DE][8×16 字形号]` + 独立字形表，
  渲染器挂在 `$01:FCA5`，槽位由 **VRAM 光标**推导（三行同屏，只有光标能区分），
  基址 24/28/32，每段 4 槽。
- 两条路径都**不占字形池的槽位、不进着色、不保护任何瓦片**，正文的着色窗口保持
  `list=9`、`SLOTS=36`、池子 923 字形不变。

**踩过的坑（都是实机才暴露的）**：

1. **8×16 字形碎成横线** —— `render8x16` 把 16px 字面缩到 8 列再二值化，沿用 16×16 的
   阈值 140 会让笔画掉到阈值以下。改用独立的 `GLYPH8_THRESH = 100`。
2. **进状态画面黑屏** —— 标签钩子开头 `REP #$30`（X 变 16 位），返回时只写了 `SEP #$20`，
   X 留在 16 位。解释器自己不在意，但它的调用方 `$FA8B` 用 `LDX $1BA6` 读角色索引，
   16 位会读两个字节，索引整体错位。改成 `SEP #$30`。
3. **顶部 `-- STATUS --` 行乱码（未修）** —— 那行是脚本里唯一的**字面瓦片块**，解释器把
   字节直接写进 tilemap，不走字库码路径，所以钩子看不到它、也没人拦着池子用它。
   **对话绘制**留下的汉字就显示在那一行上。把瓦片加进保护集会牺牲着色窗口
   （`list=9`→`list=4`）；从字体块 DMA 恢复字形内容有效但会让解释器的块循环跑飞，
   根因未查清（按我读到的循环逻辑，原版也该出错，说明理解有偏差）。

### 5.7 残留行（上一条消息留在屏幕上的碎片）

旧消息的行还留在屏幕上，格子却指向已被复用的槽位 ⇒ 汉字碎片。修法是在抽屉入口
（`JSL $3E:C400`）门控 `($036E - $0391) & 0x0F == 1` 且列 1..4 时，把 `$0391` / `$0391-1`
两行写空；**队列没空间就跳过，绝不从抽屉里调用 VBlank 刷写器**（那是整屏乱码的根因）。

### 5.8 彩色横条（本项目最隐蔽的 bug）

说话人标签的字模原先放在瓦片 460–510（VRAM `$DCC0-$DFFF`）。那片字节**同时被字符基址
`$C000` 的图层当图块表读** ⇒ 每画一次标签就把场景某行变成彩色碎片。
修法：标签搬回字库窗口（`OUTSIDE_PAIRS = []`）。`checkband.py` 从成品 ROM 静态断言：
槽位表所有条目高位为 0（瓦片全在 0..255）+ 提示表瓦片不在抽屉可达范围内。

## 6. 校验体系（为什么值得写九个脚本）

模拟器截图只能证明"这一刻看起来对"，证明不了"结构上不可能错"。所以校验分三层：

| 层次 | 脚本 | 验证什么 |
|---|---|---|
| 数据一致性 | `check16` | 1013 条文本 round-trip；字形与全新渲染逐字节一致；516 条人名记录 |
| **指令级仿真** | `verify16` | 用自写 65816 解释器 + PPU/DMA 模型，逐字节跑真实绘制流程：字形 DMA（通道/模式/源地址/长度）、写入 VRAM 的字形内容、写进 `$0B00` 的 DMA 脚本、行清空语义、延迟绘制索引回归 |
| 结构性不变量 | `checkband` `checkchoice` `checkmenu` | "横条不可能回归""选择框的瓦片不可能被覆盖""菜单标签码指向正确的池槽位" |
| 定向单测 | `test_stalerow` `test_menuclose` `test_menuload` | 三类 stub 的边界用例；`test_menuload` 直接在 65816 模型里跑上传器，逐条核对队列条目的 VRAM 地址/`$2115`/字节数/32 字节数据 |
| 交付一致性 | `ipsverify` | 交付 IPS 打在原版上 == 交付 ROM（逐字节） |

**`test_menuload.py` 的价值**：它逮到了两个靠"看截图猜"根本定位不了的 bug（见 §7.4）。
**能跑代码的模型比截图值钱。**

## 7. 技术要点（给学习者）

### 7.1 LoROM 地址换算

```
ROM 偏移 O  →  CPU 地址：bank = O >> 15，addr = $8000 + (O & 0x7FFF)
```
例：`0x01FA30` → `$03:FA30`；`0x1F0000` → `$3E:8000`。
**文件偏移 / CPU 地址 / WRAM / VRAM（还要注明字节还是字地址）必须分开记**，混起来必错。

### 7.2 文字渲染链（先反查链，再找字库）

不要一上来就"在 ROM 里搜字库"——假候选会淹死人。正确顺序是从屏幕上的已知字反查：
找到绘制点 → 看它写哪两个 tilemap 条目 → 看它从哪张表取瓦片 → 再看字模从哪来。
本作的链条：

```
文本字节 → 抽屉 $03:FA30（被我们换成 JML $3E:8200）
        → FA[code] / FB[code] 取瓦片 → 上传队列 → VBlank 刷写器 $008385 → VRAM
字模：字体块 ROM 0x0F8000（2bpp，16 字节/瓦片），游戏整块拷进 VRAM $C000
```
**实测确认**：运行中的 VRAM `$C000+瓦片*16` 与 ROM 字体块逐字节相同（受保护的瓦片）。

### 7.3 图形文字 ≠ 文本

选择框、命令窗口、状态画面、HUD 都是**用瓦片号直接画的**，不走文本编码。
把它们当文本处理（比如按 FA/FB 换算、或做 kana 改写）会破坏数据。判断方法：
看那段数据里有没有 `(瓦片号, 属性)` 成对出现、有没有 `$24` 这类属性字节、有没有指向自己的地址表。

### 7.4 三个真 bug 的复盘（都很典型）

| bug | 现象 | 根因 | 教训 |
|---|---|---|---|
| 钩子重放不全 | **一进对话就黑屏** | `$03:F0F8` 处 5 个字节是 `LDA $0392 / ASL A / TAX` **三条**指令，我只重放了第一条就跳回 `$F0FB` —— 那里已经被我自己的 JML 覆盖成 bank 字节 | 打 JML 钩子必须**重放全部被吃掉的指令**，返回地址要落在完整指令边界上；而且这个派发器**选择框也在用**，钩子该挂在更专一的位置（现挂在命令窗口自己的 `$03:F841`） |
| 地址冲突 | 死机 | 上传器放在 `$3E:C400`，那正是**残留行 stub 的地址**，抽屉每画一个字都 `JSL` 它 ⇒ 抽屉跳进菜单代码 | 新增 stub 前先列一张 scratch 地址表；构建里加**重叠断言** |
| 寄存器宽度 | 执行到垃圾 | 用了 `REP #$20`（只清 M 标志）却写 16 位 Y 立即数 ⇒ 程序计数器错位；收尾 `STX $09DF` 前没 `SEP #$30`，会多写一字节把队列页号改了 | `REP #$30` 才同时清 M/X；**改宽度后立刻回头检查所有立即数长度和存储宽度** |

### 7.5 工具与陷阱

* **EmuHawk（BizHawk）**：`client.getpixel` 在这个版本**不存在**——历史记录里那个"横条检测器"从来没工作过，
  "0 帧"不是证据。要像素就截图后离线分析。`client.screenshot(name)` **不加扩展名**；ROM 必须绝对路径；
  内存域只有 `WRAM/VRAM/CARTROM`（没有 CGRAM/OAM）。
* **snes9x**：F1 存即时存档（`Saves/<rom>.001`），`read_frz.py` 能解析出 VRAM/SRAM/RAM；
  它在 `stdout.txt` 打印 `CRC32: xxxxxxxx, Checksum OK`，用它确认跑的是哪一版。
  窗口抢焦点很顽固：先发一次 ALT 键（让本线程算"最后输入"）再 `SetForegroundWindow` 才有效。
* **`sim65816.py`**：离线跑钩子代码，能在没有模拟器的情况下验证 stub 的每一条队列条目。

### 7.6 "保持原版"也要验证

作者要求 HUD/状态画面保持原版。旧版为了省瓦片把状态画面的假名**改写成平假名**（同音不同字）——
严格说已经不是原版了。实测发现打开 `HUD_ORIG=1` 后保护瓦片数、自由瓦片对、槽位数、着色窗口
**完全不变**（之前"需要 22 对瓦片"的结论是把死代码道具名表也算进去了），于是默认打开：
状态画面的绘制脚本现在与原版**逐字节相同**。

### 7.7 证明"死代码"再省瓦片

道具名表（110 条）占着字库瓦片。证明它是死代码的三条证据：全 ROM 只有 `$01:F7CC` 一处会画它；
该入口在 ROM 里**没有任何调用/跳转/指针表引用**（`JSR/JMP/JSL` 全形式扫描 0 命中）；
它的状态字节在开机、标题、开场、对话中始终为 0。三条都成立才敢把它的瓦片让出来。

### 7.8 字体渲染的"方框底边缺口"

Unifont 给 日/白/石/苦/否 这类"下方有口"的字，把口的底线画在第 14 行、第 15 行还留着两条竖边，
看起来像没封口。判据：**第 15 行的墨迹是第 14 行（一条连续横线、长度 ≥5）的子集** ⇒ 清掉第 15 行。
对全库 966 个汉字扫过，命中 62 个，逐个人眼核对全部变好、无误伤。`GLYPH_STRAY=0` 可关。

## 8. 怎么读这个仓库（学习路径）

1. **`交接文档.md`** —— 先看当前状态、红线、未完成项、11 条坑。它是最新的一份，也是最短的。
2. **`notes/current-state.md`** —— G0–G6 阶段划分与构建指针。
3. **`汉化完成度报告.md`** —— 哪些做了、哪些有意保留、哪些没做（不含糊）。
4. **`cnbuild5.py`** —— 从 `main()` 往下读。重点看：编码 → 图着色 → 写 ROM → 装钩子。
   每个钩子/stub 上面都有一段注释说明**为什么这么做、踩过什么坑**。
5. **`verify16.py` + `sim65816.py`** —— 看"怎么在没有模拟器的情况下证明绘制正确"。
6. **`checkband.py` / `checkchoice.py` / `checkmenu.py`** —— 看"怎么把一次修好的 bug 变成不可能回归的断言"。
7. **`hw/*.lua`** —— 需要真机行为时才用；注意 EmuHawk 的坑（§7.5）。

**方法上的三条经验**（比具体地址更有价值）：

* **从屏幕反查链条，别从 ROM 盲搜资源**；
* **每次只改一个变量，冷启动复现预期变化，然后验证回退**；
* **能跑代码的模型（`sim65816`）> 仿真截图 > 人眼看图**；断言 > 记录。
